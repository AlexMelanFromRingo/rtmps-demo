# Политика безопасности

## Поддерживаемые версии

Релизов с тегами пока нет. Исправления безопасности выходят только в **последний коммит
ветки по умолчанию**. Старые коммиты и форки не поддерживаются. Обновляйтесь до актуального состояния
ветки, прежде чем сообщать о проблеме.

| Версия | Поддержка |
|---|---|
| ветка по умолчанию, последний коммит | ✅ |
| всё остальное | ❌ |

## Как сообщить об уязвимости

**Не открывайте публичный issue.** Сообщите приватно через GitHub:
**Security → Report a vulnerability** в репозитории
([прямая ссылка](https://github.com/AlexMelanFromRingo/rtmps-demo/security/advisories/new)).
Если кнопки нет, приватные отчёты в репозитории выключены. Тогда откройте issue
с просьбой связаться, не раскрывая подробностей.

В отчёте укажите:
- компонент (api, worker, ingest, srt-gateway, edge, web) и коммит;
- шаги воспроизведения или PoC и ожидаемое/фактическое поведение;
- оценку последствий (что получает атакующий);
- ваши настройки, если они не по умолчанию (`.env` **без секретов**).

Ориентиры: подтверждение получения — в течение 3 рабочих дней, первичная оценка — в течение
7 дней. Исправление выпускается раньше публичного раскрытия. Срок раскрытия согласуем,
по умолчанию до 90 дней. Если хотите, вас упомянут в описании исправления.

Вне рамок: атаки, которые требуют доступа к внутренней сети или к `.env`; DoS
объёмом трафика; развёртывания с секретами по умолчанию или без TLS вопреки
[чек-листу](docs/OPERATIONS.md); уязвимости сторонних образов без способа эксплуатации в StreamHub.

## Модель безопасности

Ниже описано, как устроена защита. Это поможет понять, что считать уязвимостью.
Подробнее — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) и [docs/OPERATIONS.md](docs/OPERATIONS.md).

### Границы доверия

- Снаружи доступны только edge (сайт, `/api`, `/hls`) и входы ingest: RTMP 1935, SRT 8890/udp,
  универсальный SRT 8891/udp, WHIP 8889, WebRTC 8189. Всё остальное — во внутренней сети: RTSP 8554,
  API и метрики MediaMTX 9997/9998, API 3000, метрики воркера 9100, srt-gateway 9101, Postgres,
  Valkey, SeaweedFS, Prometheus/Grafana.
- Edge отвечает `404` на `/internal/*`, `/metrics`, `/healthz`, `/readyz`. Метрики и служебные
  эндпоинты наружу не проксируются.

### Ключи трансляции

- Формат: `live_` + 32 символа из алфавита в 57 знаков (≈ 186 бит), генерация через
  `crypto.randomBytes` без смещения (rejection sampling).
- Каждую публикацию (RTMP, SRT, WHIP и универсальный SRT-шлюз) авторизует control plane по ключу из БД.
- Чтение сырых потоков с ingest разрешено только воркерам: внутренний пользователь `transcoder`
  и `INTERNAL_SECRET`. Зрители получают только HLS из объектного хранилища.
- Сброс ключа (`POST /api/channel/stream-key`, не чаще 10 раз в час) сразу отклоняет старый
  ключ для новых публикаций. Идущий эфир не обрывается.
- Ключи и секреты вырезаются из ошибок ffmpeg/ffprobe, которые попадают в логи и в БД
  (`server/src/lib/redact.ts`).
  В Prometheus путь MediaMTX (содержит ключ) заменяется необратимым хэшем
  (`deploy/observability/prometheus/prometheus.yml`).
- `SRT_PASSPHRASE` включает шифрование SRT на универсальном входе (порт 8891).

### Внутренний секрет (`INTERNAL_SECRET`)

- Им подписываются вызовы ingest-узлов, srt-gateway и воркеров к `/internal/*` (заголовок
  `Authorization: Bearer …` или Basic, не в URL — чтобы не попадать в access-логи). Сравнение
  выполняется за постоянное время.
- API **не стартует** с секретом по умолчанию, если `PUBLIC_RTMP_URL` или `PUBLIC_WHIP_URL`
  указывают не на localhost (обойти можно только явным `ALLOW_DEFAULT_SECRET=true`).
- Секреты в БД (TOTP-сиды, ключи рестрима на сторонние площадки) зашифрованы AES-256-GCM. Ключ
  выводится через HKDF из `DATA_ENCRYPTION_KEY`, а если он не задан — из `INTERNAL_SECRET`.
  В этом случае смена `INTERNAL_SECRET` делает сохранённые секреты нечитаемыми, поэтому
  в продакшене задайте отдельный `DATA_ENCRYPTION_KEY`.

### Аккаунты и сессии

- Пароли: scrypt (N=2¹⁵, r=8, p=1, соль 16 байт, NFKC-нормализация), длина 8–128 символов.
  Сравнение за постоянное время. Для несуществующего логина выполняется фиктивная проверка,
  чтобы время ответа не выдавало, есть ли пользователь.
- Сессия: 256-битный случайный токен в cookie `sid` (`HttpOnly`, `SameSite=Lax`, `Secure` при
  `COOKIE_SECURE=true`, срок `SESSION_TTL_DAYS`, по умолчанию 30 дней). В БД хранится только SHA-256 токена.
  Пользователь видит свои сессии и может завершить их. Смена пароля завершает все остальные сессии.
- Двухфакторная аутентификация TOTP (RFC 6238: HMAC-SHA1, 6 цифр, шаг 30 с, допуск ±1 шаг):
  - сид 160 бит, хранится зашифрованным;
  - каждый шаг принимается один раз, так что повтор перехваченного кода не сработает;
  - 8 одноразовых резервных кодов, в БД хранятся только их SHA-256;
  - отключение 2FA требует пароль и код.
- Аватары: загрузка до 3 МБ, остальные тела запросов ограничены 64 КБ.

### CSRF и заголовки

- Cookie `SameSite=Lax`.
- Изменяющие запросы (`POST/PUT/PATCH/DELETE`) принимаются только с
  `Content-Type: application/json` (иначе `415`), так что простую форму с чужого сайта не отправить.
- Если есть заголовок `Origin`, его хост должен совпадать с `Host` (иначе `403`).
- IP клиента берётся ровно из `TRUST_PROXY_HOPS` прокси, подделанный `X-Forwarded-For` не учитывается.
- SPA отдаётся с `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`,
  `Referrer-Policy` и `Permissions-Policy` (камера, микрофон и захват экрана — только свой origin).

### Ограничение частоты запросов

Счётчики с фиксированным окном лежат в Valkey. **Если Valkey недоступен, лимиты не применяются
(fail-open)**, чтобы падение кэша не ломало вход и стриминг. Ответ при превышении — `429`.

| Действие | Лимит | Ключ |
|---|---|---|
| регистрация | 20 / 10 мин | IP |
| вход | 30 / 5 мин и 10 / 5 мин | IP и логин |
| код 2FA при входе | 8 / 5 мин | пользователь |
| включение / отключение 2FA | по 10 / 5 мин | пользователь |
| смена пароля | 10 / 10 мин | пользователь |
| сброс ключа трансляции | 10 / час | пользователь |
| загрузка аватара | 20 / час | пользователь |
| подписки (follow) | 60 / 10 мин | пользователь |
| поиск | 120 / мин | IP |
| heartbeat зрителя | 240 / мин | IP |
| просмотры VOD | 120 / мин | IP |
| SSE оверлея / тестовое оповещение | 60 / мин и 20 / мин | IP и пользователь |

Сверху nginx на edge ограничивает `/api/` до 30 запросов/с на IP (burst 60), а одновременные
SSE-подключения — до 20 на IP.

### Прочее

- Объектное хранилище: анонимно доступен только `GetObject` (`S3_PUBLIC_READ=true`). Запись и листинг
  закрыты. Edge не передаёт в S3 заголовки `Authorization` и `Cookie`.
- Рестрим на сторонние площадки: разрешены только схемы `rtmp://`, `rtmps://`, `srt://`. Адреса
  из частных и служебных диапазонов блокируются (защита от SSRF; снять блокировку можно только
  явным `RESTREAM_ALLOW_PRIVATE=true`). Ключ площадки хранится зашифрованным, в API видны лишь
  последние 4 символа.
- Оверлей для OBS доступен по секретному URL (64 hex-символа), который можно перевыпустить.
- Grafana из `docker-compose.observability.yml` по умолчанию слушает только `127.0.0.1`,
  анонимный доступ выключен. Пароль по умолчанию годится только для локальной разработки.
